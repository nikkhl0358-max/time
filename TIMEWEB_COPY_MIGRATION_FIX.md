# Timeweb: исправление PostgreSQL COPY при переносе пользователей — 06.11.2026

## Симптом
После восстановления PostgreSQL в журналах приложения около 17:49–17:57 МСК повторялись:

`another command is already in progress`

и `error ignored in rollback on <psycopg.Connection [ACTIVE]>`.

Это **уже не** сообщение о том, что PostgreSQL остановлена. Сервер принимал соединения к базе `timetable`, но программа пыталась выполнять следующий SQL-запрос, пока предыдущая операция `COPY ... TO STDOUT (FORMAT BINARY)` не была прочитана до конца.

## Точное исправление
В `auth_store.py` функция `_legacy_users()` при первом переносе сотрудников считывала поле с JSON проекта и завершала обработку, **не потребляя завершающий маркер бинарного COPY (`-1`) и конец COPY-потока**. После этого `INSERT INTO auth_user_store` на том же соединении мог возвращать `another command is already in progress`, транзакция откатывалась и миграция повторялась при следующем запросе.

Теперь `_CopyBinaryField.finish()`:

1. Дочитывает остаток JSON-поля, не помещая весь проект в память.
2. Проверяет завершающий маркер бинарного COPY.
3. Обязательно дочитывает COPY до EOF, освобождая состояние соединения перед следующим SQL.
4. При повреждённом потоке прерывает миграцию с ошибкой — вместо создания пустого списка пользователей.

Обработан и старый двойной формат JSON. Модуль `pg_compat.py`, SQL-схема проекта, frontend, API расписания, механизмы сохранения и планировщик **не изменены**.

## Проверки

Запустить локально:

```bash
python tests/regression/test_auth_store.py
python tests/run_regression.py
```

Тест `test_migration_fully_drains_copy_before_insert` **воспроизводил реальную строку ошибки до исправления** и проходит после него. Есть дополнительные тесты на большой JSON, раннее расположение массива `users`, двойной JSON и повреждённый конец COPY. Полный офлайн-набор: 28/28 успешных групп проверок.

Интеграционный тест с настоящей PostgreSQL Timeweb и браузером здесь не выполнялся. Не считать production исправленным до успешного входа.

## Установка и проверка

1. Сделать резервную копию существующей PostgreSQL.
2. Убедиться, что в Adminer работает база **`timetable`** (не путать с `default_db`).
3. Обновить проект новым архивом; `DATABASE_URL` должен указывать на ту же существующую базу. **Не создавать новую БД и не удалять учётные записи**.
4. После успешного деплоя один раз открыть `/api/auth/session`, затем попробовать войти со старым логином и паролем.
5. Если `setupRequired: false`, пользователи определены. Если `setupRequired: true` или снова 503, **не регистрировать администратора**, а проверить свежий журнал приложения после времени деплоя.
6. В Adminer можно безопасно проверить факт миграции (запрос не показывает пароли):

```sql
SELECT to_regclass('public.auth_user_store') AS auth_table;
SELECT store_key, length(users_json) AS users_bytes FROM public.auth_user_store;
```

Второй запрос выполнять только если таблица уже существует.

## Безопасность

Пароль PostgreSQL был ранее опубликован в чате; после резервной копии сменить его в Timeweb и одновременно обновить секрет `DATABASE_URL` приложения. Не публиковать новую строку подключения.

Если возникают другие ошибки (`connection timeout`, `FATAL: ... shutting down`, `out of memory`), они требуют отдельной проверки состояния PostgreSQL: исправление COPY не лечит аварии самого сервера базы.
