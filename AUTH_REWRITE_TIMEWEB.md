# Исправление авторизации и нагрузки PostgreSQL (Timeweb, 06.11.2026)

## Почему было плохо

В предыдущей версии каждое обращение к серверному API вызывало запрос `value_json::jsonb -> 'users'` для большого `kv_store.schedule-data-v2`. PostgreSQL каждый раз разбирала всё расписание целиком. В журналах за 6 ноября обнаружено принудительное завершение серверного процесса, выполнявшего этот запрос. Даже после оптимизации прочих участков запрос оставался в обработчике входа.

## Что теперь

- `auth_store.py` — отдельный **маленький** набор учётных данных в PostgreSQL: `auth_user_store(store_key, users_json, updated_at)`.
- Первый запрос к авторизации при работающей БД **один раз** переносит список пользователей из старого проекта. Он считывает исходный `value_json` через **потоковый PostgreSQL COPY BINARY** и выделяет только корневой массив `users`, не преобразуя большое расписание в `jsonb` и не загружая целый проект в память Python.
- Миграция защищена транзакционной advisory lock от параллельного создания записей. Если база, исходный ключ или JSON недоступны/повреждены, операция завершается ошибкой без создания пустого набора учётных записей.
- Последующие входы и проверки сессии обращаются только к `auth_user_store`, не читают `kv_store`.
- Изменение личного пароля и обновление старого SHA256 до scrypt обновляют только маленькую строку, не сериализуют расписание.
- Добавление, удаление или смена роли через интерфейс главного администратора сохраняются **в той же транзакции**, что и соответствующее изменение JSON рабочего проекта.
- Чтение проекта для редактора получает актуальный список пользователей поверх прежнего JSON. Старый хеш из отложенного автосохранения **не может** затереть текущий хеш.
- SQLite-режим сохранён для локальной разработки. Алгоритмы расписания, таблицы занятий, структура `schedule-data-v2`, публикация, генерация и отложенная загрузка разделов не изменялись.

## Безопасная установка

1. Убедиться, что **исходная PostgreSQL Timeweb работает**. Код не способен починить PostgreSQL, когда она сама останавливается (`FATAL: the database system is shutting down`).
2. **Сделать резервную копию PostgreSQL** (штатными средствами Timeweb). Не создавать новую базу и не импортировать пустой проект.
3. Заменить файлы проекта на содержимое этого ZIP, сохранив текущие переменные окружения и подключения. Новая версия использует тот же `DATABASE_URL`.
4. Дождаться успешного деплоя. При первой проверке `/api/auth/session` может выполниться одноразовая миграция. На последующих запросах она не повторяется.
5. Проверить `/api/auth/session`: при наличии старых сотрудников вернётся `setupRequired: false`, затем проверить вход старым логином и паролем.
6. Проверить `/api/editor/schedule-data-v2?section=bootstrap` после входа и открыть нужную группу, без какого-либо создания нового проекта.
7. После резервной копии **сменить пароль PostgreSQL**, который ранее был раскрыт в переписке, и обновить секрет `DATABASE_URL` в Timeweb. Не публиковать полный URL с паролем.

### Если появляется ошибка

- `STORAGE_UNAVAILABLE` (HTTP 503): БД недоступна по сети/находится в перезапуске; проверить Timeweb PostgreSQL, сетевые правила, лимиты памяти, перезапуски и реальные логи БД.
- `AUTH_MIGRATION_UNAVAILABLE` (HTTP 503): не удалось безопасно прочитать старый проект или подготовить учётные записи. **Не регистрировать главного администратора заново**; сначала проверить журналы приложения и БД. Для очень старого двойного JSON-проекта свыше 4 МБ требуется отдельный контролируемый перенос.
- `setupRequired: true` при том, что сотрудники раньше были: **остановиться и проверить, что `DATABASE_URL` указывает на прежнюю базу**. Не создавать нового админа без проверки.

## Совместимость и откат

В новой версии после миграции **таблица `auth_user_store` является источником истины для логинов, ролей и паролей**. Поле `users` внутри `kv_store` остаётся для совместимости с расписанием и может отражать старый пароль до следующего сохранения проекта. Это безопасно для *новой* версии, потому что она проверяет только отдельную таблицу. **Но откат только к старому коду после смены пароля или ролей может снова использовать старые учётные данные.** Перед откатом нужно отдельно согласовать перенос актуальных пользователей обратно или восстановить совместимую пару «код + резервная копия БД». Самостоятельно очищать таблицу `auth_user_store` нельзя.
